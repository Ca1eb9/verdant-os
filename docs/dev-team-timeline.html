8-week timeline: 3 development sprints (Sep 21 – Nov 1) + 2 weeks integration and Showcase prep (Nov 2 – 15).

Caleb Adi Jameson

System architecture

How the system works

The farm is a distributed system — no single service knows everything or does everything. Each component has one job, and they communicate through MQTT, a lightweight publish/subscribe messaging protocol. A broker (Mosquitto) runs on the Raspberry Pi. Any device or service can publish a message to a topic, and any other device or service that has subscribed to that topic will receive it. Services never import or call each other directly — MQTT is the only interface between them. This means each service can be developed, tested, and restarted independently.

The robot IS the tray. Each robot carries a plant and moves it to water stations, light stations, and the charging dock. The ESP32 microcontroller on each robot runs FreeRTOS firmware with four concurrent tasks that handle motors, sensors, navigation decisions, and network communication independently.

The Raspberry Pi runs several independent Node.js services. The orchestrator is the brain — it tracks robot state, schedules plant care tasks, and sends navigation commands. The ingester (already built) records all telemetry to a local SQLite database. The alert engine monitors sensor values and flags threshold violations. The dashboard API serves stored data to the web dashboard. The Supabase bridge syncs local data to the cloud for remote access.

The dashboard is a React app that works in two environments: on the farm's local WiFi it connects directly to the Pi for real-time data, and on the internet (Vercel) it connects to Supabase instead. It detects which environment it's in automatically.

Navigation works through RFID tags placed at fixed positions in the farm. The farm's layout is defined as a graph of nodes and edges in a topology file. BOTH the orchestrator and the robot compute shortest paths; this allows for on-board route planning. The robot reads tags as it drives to know where it is.

Key conventions

MQTT topics follow a consistent naming pattern — review the topics file in farm-controller/shared/src/topics.ts to see the full convention and use the provided helper functions rather than writing topic strings by hand.

All MQTT message payloads are JSON objects matching TypeScript interfaces defined in farm-controller/shared/src/types.ts. Before starting any task, read through the relevant types in this file to understand the data structures your service will produce or consume.

The shared package (@farm/shared) also includes a typed MQTT client wrapper, navigation utilities (Dijkstra, heading math), and topic helper functions. Familiarize yourself with everything in farm-controller/shared/src/ — it's the foundation every service builds on.

Task reference

Each task describes what to build and where it fits. The shared package (farm-controller/shared/src/) defines all message types, topic conventions, and utilities — review it before starting any task to understand the data structures and interfaces your service will use.

Caleb

Orchestrator core

The central decision-making service. Subscribes to robot telemetry and events over MQTT, maintains a state model for each robot, runs a state machine to track lifecycle transitions, and publishes navigation commands when a robot is ready for its next task.

Requirements
  • New service in farm-controller/orchestrator
  • Subscribe to the appropriate telemetry and event topics for all robots (check the topics file for wildcard patterns)
  • Maintain an in-memory state object per robot: current position, battery, heading, assigned task, path progress, and a timestamp for the last message received
  • Implement the state machine that was designed for this project (Idle → En Route → Working → Idle, charge cycle, stopped, error states). The robot's reported status and task are the source of truth; events are a fast path, and telemetry reconciles anything missed. See docs/firmware-architecture.md.
  • Watchdog: periodically check whether each robot has gone silent for too long. If so, mark it as lost and publish an alert.
  • When a robot is idle, take the next task from the queue, compute the shortest path using the navigation utilities in the shared package, and publish a command with the target (and optionally the node id path)
  • If a robot's battery drops below a configurable threshold, send it to the dock. The robot keeps its task and resumes it after charging; work is only re-queued if the robot reports it no longer has the task. A pending stop takes priority over the low-battery return.
  • Operators can stop, resume, return to dock, and cancel a robot's current task (even while the robot is lost)
  • All tunable values (timeouts, thresholds, intervals) load from a config file at startup
Approach
  • Start by subscribing to telemetry and logging every position update — verify the MQTT pipeline works
  • Add the state object and update it from messages
  • Add the state machine as a handler that reacts to events
  • Add path computation and command publishing, and test against the simulator in non-autonomous mode

Depends on: shared package, Mosquitto broker, simulator (for testing)

FreeRTOS infrastructure + navigation task

The ESP32 firmware architecture. Establishes four concurrent tasks with different priorities, defines the queue-based communication between them, and implements the navigation task — the firmware's decision-making brain that manages path following and turn execution.

Requirements
  • Four FreeRTOS tasks: motor (highest priority), sensor, navigation, and communications (lowest priority). Motor and timing-critical tasks go on one core; networking goes on the other to avoid WiFi blocking motor control.
  • Define struct types for each queue's messages — these are the interfaces between tasks. The other team members write their task implementations against these structs.
  • Shared volatile flags for safety-critical signals that need to be checked every cycle without queue overhead
  • Navigation task: implements the robot's state machine, processes incoming commands from the orchestrator, follows RFID waypoint paths using heading math, and publishes events on state transitions
  • Store the farm's navigation graph in flash memory for autonomous return-to-dock capability. Dock tag ID is a hardcoded constant.
  • loop() is empty — all logic runs in tasks

Depends on: ESP32 hardware, development environment (PlatformIO or Arduino IDE)

RFID navigation logic + integration

Combine the navigation task with Jameson's sensor and motor tasks on real hardware. The nav task receives RFID positions from the sensor task, computes turns, sends drive commands to the motor task, and reports progress back to the orchestrator. Joint work with Jameson.

Requirements
  • Match incoming RFID tag UIDs against the on-board graph to determine position
  • At each waypoint: compute the heading to the next node, determine the turn, drive until the next tag is read
  • Publish events when the robot arrives at its destination and when it begins its action
  • Handle missed reads: if no tag appears within a timeout while driving, stop and report the issue
  • Physical tuning: RFID read distance, motor speed, turn calibration

Depends on: FreeRTOS skeleton, Jameson's sensor and motor tasks, physical RFID tags placed in the farm

Survival overrides

Safety behaviors in firmware that protect the robot regardless of whether the Pi is online. These override all other logic except a stop. Joint work with Jameson.

Requirements
  • Battery thresholds at three levels: warn, force return to dock, kill motors. Checked every loop iteration before normal logic runs.
  • Obstacle flag: set by the sensor task, checked by the motor task — hard stop when triggered
  • No Pi heartbeat watchdog: losing the Pi is not a reason to return to dock. The robot keeps working on its task until the battery thresholds send it to charge.

Depends on: RFID navigation, motor control

Plant scheduler

An addition to the orchestrator that automatically generates care tasks based on per-plant-type schedules (watering intervals, light duration, etc.).

Requirements
  • Read plant care schedules from the orchestrator config
  • For each robot, determine its plant type and track when it was last watered and how much light it has accumulated
  • Enqueue water and light tasks when intervals elapse
  • Priority ordering: charge > water > light

Depends on: orchestrator core

Adi

Alert engine

A standalone service on the Pi that watches the robots' and the shelves' sensor data flowing through MQTT and publishes alert messages when any reading falls outside acceptable ranges. It subscribes, evaluates and publishes; the only state it keeps is in memory, per device and metric, for the hold time, deadband and cooldown below.

Requirements
  • New service in farm-controller/alert-engine (use the ingester's project structure as a reference)
  • Subscribe to robot telemetry on MQTT. Review the shared types to understand which fields contain sensor readings and which topic carries this data.
  • Shelf sensors (required): also subscribe to farm/shelf/+/sensors (ShelfSensorData, from the shelf bridge, docs/shelf-sensors.md) and alert, per shelf, on temperature_c, humidity_pct, water_temp_c and ph outside their ranges, and on water_level_ok: false (critical: the reservoir is below the level sensor). A null field means that sensor didn't read: raise nothing for it (the shelf bridge already alerts when a shelf goes silent). There are no light thresholds yet. Start from the dashboard's ranges in web/src/lib/alerts.ts (THRESHOLDS, warning and critical, with their deadbands) so the dashboard and the Pi agree; the dashboard's own alerts are a stand-in until this service runs.
  • Load a JSON config file that defines acceptable ranges for each sensor metric (e.g. minimum humidity, maximum temperature). Design the config format based on the threshold types already defined in the shared package.
  • When a reading violates a threshold, construct an alert message (see the alert type in shared) and publish it to the appropriate alerts topic
  • Hold time: raise an alert, or escalate a warning to critical, only after the readings have stayed out of range for a hold time (30 s on the dashboard), so a one-off spike or bad read raises nothing. Easing or clearing is immediate.
  • Deadband: once raised, an alert clears only when the value is back inside its limit by a per-metric margin (dashboard: 1 °C air, 3 % humidity, 0.3 °C water, 0.1 pH), so a value sitting on a limit doesn't flap. The DHT11 reports whole degrees and percent, so without it air readings cross a limit on every report.
  • Hold time and deadbands go in the JSON config: SensorThreshold in the shared types has neither yet, so adding them is a shared-type change (update its copies in the same PR)
  • Prevent alert spam: if the same metric on the same device is still out of range, don't re-alert within a cooldown window
  • Stretch: For critical-severity alerts, optionally send notifications via SMS or email to a contact list in the config. Research available APIs (Twilio, Resend, etc.) and choose one that fits.
Approach
  • Start by connecting to MQTT and logging every incoming telemetry message to verify the pipeline
  • Add threshold checking for one metric first, then generalize
  • The whole service is roughly 80–100 lines of code

Depends on: shared package, Mosquitto broker. Test against the simulator, which publishes telemetry with sensor readings, and publish shelf readings with mosquitto_pub -t farm/shelf/shelf-1/sensors (or run the shelf bridge with a node).

Supabase bridge

A service on the Pi that syncs data between the local MQTT bus and Supabase in the cloud. It does three things: relays remote commands from Supabase into the local system, pushes local telemetry up to Supabase so the remote dashboard has data to display, and tells the remote dashboard the farm is online. This must be completed before the dashboard's remote data source, because that has nothing to read without it.

Requirements
  • New service in farm-controller/supabase-bridge, run on the Pi like the others (docs/PI-SERVICES.md, "Adding a service"). Tunable values in a config file.
  • Supabase project: use the team project Caleb owns (docs/SUPABASE-SETUP.md); ask him for an invite. Its tables are already defined in web/supabase/*.sql — write to those, and change the schema only by editing those files in a PR. Take the project URL and the secret (service_role) key from the project's settings into SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY in /etc/verdant/supabase-bridge.env, with a checked-in deploy/env/supabase-bridge.env.example. Never commit or share the key (the repo is public). The project only allows private Realtime channels, so create every channel with { config: { private: true } }; the secret key may use any channel name.
  • One bridge per farm: the project serves every farm, and each farm's Pi runs its own bridge. Read FARM_ID from supabase-bridge.env: the id of that farm's row in the farms table (Caleb adds the rows, docs/SUPABASE-SETUP.md). Check at startup that the row exists and exit with a clear error if not. Every row the bridge writes carries farm_id = FARM_ID, and it only ever reads or updates its own farm's rows. MQTT carries no farm id: one Pi, one broker, one farm.
  • Inbound (commands): the dashboard on Vercel already inserts operator commands into the remote_commands table (web/src/app/api/commands/route.ts: id, farm_id, robot_id, command as a RobotCommand, issued_by, issued_at, status pending / sent / failed, error). Subscribe to this farm's new rows with Supabase Realtime (filter farm_id=eq.<FARM_ID>), and also fetch this farm's pending rows on every (re)connect, since Realtime misses rows inserted while the bridge was offline. Never relay another farm's command.
  • For each pending row: publish { id, robot_id, command, issued_by, issued_at } (a RemoteCommand) to TOPICS.commands.remote, then set status to sent, or failed with an error, and processed_at to now(). Update only while it's still pending, so a restart or a second bridge never sends it twice. Validate each row before publishing. The orchestrator already handles this topic; jog is local only and the route refuses it.
  • Prevent replaying stale commands: mark a row older than a configured limit failed ("stale") instead of sending it. Measure its age with Supabase's clock (now() in SQL), not the Pi's: there's no clock sync.
  • Outbound: mirror the farm into the tables from web/supabase/farm_sync.sql, each row with farm_id:
    • farm/robot/+/telemetry → insert into robot_telemetry, with the Pi's receive time as received_at. Downsample: at most one row per robot every few seconds (configurable), plus one right away when its status or node changes, so the free tier's 500 MB lasts (old rows are trimmed daily).
    • farm/robot/+/state (retained) → upsert robot_state by (farm_id, robot_id)
    • farm/alerts → insert into alerts (ignore a duplicate alert_id)
    • farm/system/topology (retained) → upsert this farm's farm_topology row (by farm_id)
    • farm/shelf/+/sensors (from the Pi's shelf bridge, docs/shelf-sensors.md) → insert into sensor_events, the dashboard's environment feed, downsampled the same way: device = shelf_id, source = "supabase-bridge", ts = the reading's timestamp, air_temp_c = temperature_c, humidity_pct, water_temp_c, water_level_ok, ph and light_lux by name (each may be null). The dashboard derives °F from °C and shows light as lux. This is the only writer of sensor_events; the old laptop serial bridge is retired.
    Accumulate writes in a buffer and flush at a regular interval to stay within Supabase's rate limits.
  • Farm online (presence): while connected to the local MQTT broker, track presence on the Supabase Realtime channel farm-status ({ config: { private: true, presence: { key: FARM_ID } } }) with { farm_id, service: "supabase-bridge", online_at }, so every farm's bridge shares the channel under its own key; untrack when the MQTT connection drops. Supabase removes it on its own when the bridge loses its internet connection. The project only allows private channels, and only the secret key can track, so the dashboard can listen but never mark the farm online. The remote dashboard's connection pill follows the selected farm's key.
  • Handle internet outages without crashing — buffer outbound data (bounded) and flush when the connection resumes
Approach
  • Start with just the inbound command path: subscribe to Supabase Realtime, log each row, publish to MQTT. Verify with Mosquitto CLI tools.
  • Add presence next, then the outbound mirroring
  • Review the Supabase Realtime documentation (Postgres changes, Presence, Authorization) and the @supabase/supabase-js library

Depends on: the Supabase project set up per docs/SUPABASE-SETUP.md (Caleb), shared package, Mosquitto broker

Dashboard data flow — local + remote

The dashboard should work identically on the farm's WiFi (connecting to local services) and on the internet via Vercel (connecting to Supabase), and figure out which one to use automatically, without any user configuration. The data service layer and the local half are already built: all UI goes through the FarmDataSource interface (web/src/lib/farm/data-source.ts), and web/src/lib/farm/local-source.ts implements it over MQTT/WebSocket. What's left is the remote source and the automatic detection. Remotely the dashboard shows any farm in Supabase's farms table (the header's farm picker, web/src/components/farms/FarmContext.tsx); on FarmNet only the Pi's own farm.

Requirements
  • Remote source: a new web/src/lib/farm/remote-source.ts exporting createRemoteSource(farmId), a FarmDataSource with mode: "remote" for one farm. selectFarm() in data-source.ts already swaps in a source whenever the picked farm changes: make it create yours instead of createDashboardApiSource. Every query and Realtime subscription is filtered to that farm (farm_id=eq.<farmId>); robot ids repeat across farms. Use local-source.ts as the model:
    • subscribeRobots: load each robot's latest robot_telemetry row and its robot_state, then follow their changes through Supabase Realtime on the private channel farm-data; map them to RobotView the same way local-source.ts does (lastSeen from the row's created_at, Supabase's clock)
    • getTopology: the farm's farm_topology row, otherwise null (the default layout)
    • sendCommand / listRecentCommands: the existing /api/commands route (operator key required, farm_id in the body and the query), as createDashboardApiSource does today
    • subscribeConnection: connected while the farm's key (its id) is in the farm-status channel's presence state; otherwise offline, with a short reason in plain words (e.g. "The farm isn't online right now." or "Can't reach the cloud service."); no service names, hosts or settings in it, those go to the console. The header pill and the offline banner already follow this, so no UI work is needed.
  • Detection: replace the temporary NEXT_PUBLIC_MQTT_WS_URL switch at the bottom of data-source.ts. On the farm network the page is served from the Pi, so its origin hostname is the Pi and the broker's WebSocket listener (port 9001) is right there; on Vercel it isn't. Pick the source at runtime and register it with setFarmDataSource(). ON_FARMNET (which locks the farm picker to the Pi's farm, NEXT_PUBLIC_FARM_ID in the Pi's build) must follow the detection too. Components must not change.
  • Environment feed (shelf sensors): already behind the data source: FarmDataSource.subscribeShelves streams each shelf's latest reading, and useFarmTelemetry shows the newest. The local source fills it from farm/shelf/+/sensors; the remote stub passes null, so remotely the dashboard still polls the latest sensor_events row through /api/sensor-events/latest?farm_id=. Remote: implement it from this farm's sensor_events rows (the latest per device, then their inserts through Realtime on farm-data), and the polling can go.
  • Alerts (robots and services): already in the interface: FarmDataSource.subscribeAlerts streams the farm's FarmAlerts, newest first, to the Alerts page. The local source fills it live from farm/alerts (only alerts raised since the dashboard opened); the remote stub passes null, which the page shows as "not available here yet". Remote: implement it from this farm's alerts rows (the latest ones, then their inserts through Realtime on farm-data), newest created_at first, with alert_id deduplicated. Local: also load the earlier ones once from the Dashboard API's GET /alerts and merge them behind the live ones, the same way listRecentCommands loads GET /commands.
  • Historical data: sensor history and alerts. The live half is built for local mode: FarmDataSource.subscribeShelfHistory streams every shelf reading received since the dashboard opened (the local source keeps a day of one shelf), and the History page buckets them into its charts (useShelfHistory). What's left is the stored half: in local mode, load the selected range once from the Pi's Dashboard API and put it in front of the live readings; in remote mode, load it from the farm's sensor_events and follow new rows through Realtime. Robot telemetry and alert history work the same way, from the Dashboard API locally and from robot_telemetry and alerts remotely. Remotely the History page has no source yet and says so.
  • Supabase: the team project (docs/SUPABASE-SETUP.md). The browser uses only the publishable key (NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY, set on Vercel); every Realtime channel must be private ({ config: { private: true } }), and only farm-data and farm-status are allowed.
Approach
  • Build the remote source's subscribeConnection and subscribeRobots first, with the bridge running, and check the map and the pill on Vercel
  • Then the detection, tested both from FarmNet and from another network
  • Research Supabase Realtime's Postgres changes and Presence in the browser

Depends on: Supabase bridge (populates Supabase and the presence channel for remote mode), the Supabase project and Vercel env vars (docs/SUPABASE-SETUP.md), Jameson's Dashboard API (history in local mode), Mosquitto's WebSocket listener (already in docs/WIFI-SETUP.md)

Jameson

ESP32 communications task

One of the four FreeRTOS tasks on the ESP32. This task is the robot's link to the outside world — it connects to WiFi, communicates with the MQTT broker on the Pi, publishes the robot's status, and receives commands from the orchestrator. Runs at the lowest priority because network operations can be slow without affecting motor or sensor timing.

Requirements
  • Connect to the farm's WiFi network and the Mosquitto broker
  • Read the telemetry and event queues (populated by the nav task) and publish each message as JSON to the robot's telemetry or events topic, always sending queued events before queued telemetry. Review the shared types to understand the expected message format and field names — the JSON fields must match exactly so Pi services can parse them.
  • Subscribe to the robot's command topic. Parse incoming JSON into a command struct and push it onto the command queue for the nav task to process.
  • Handle disconnects gracefully — reconnect to WiFi and MQTT without blocking other tasks or using delay()
Approach
  • Start with a standalone sketch (outside FreeRTOS) that connects to WiFi and publishes a test message every second. Verify with Mosquitto CLI tools.
  • Move the code into the comms task function, reading from the telemetry queue instead of hardcoding values
  • Research the ArduinoJson library for JSON serialization and PubSubClient for MQTT

Depends on: queue struct definitions from the FreeRTOS skeleton, Mosquitto broker

ESP32 sensor task

One of the four FreeRTOS tasks. Reads RFID tags to determine position, measures battery voltage, and detects obstacles. Writes data to the sensor queue and sets safety flags that the motor task checks every cycle.

Requirements
  • Poll the PN532 RFID reader (I2C or SPI) at a regular interval. When a tag is present, read its UID.
  • Read battery voltage through an ADC pin and a voltage divider. Convert the raw reading to a usable percentage.
  • Read distance from the obstacle sensor (ultrasonic or IR). When the distance drops below a safety threshold, set the shared obstacle flag so the motor task stops immediately.
  • Now done: two VL53L4CX sensors set a front and a rear flag. The nav task lowers a side's stop distance (g_obstacle_*_stop_cm) while it creeps into the elevator or onto the dock; the sensor task flags against it (see COMMS-SENSOR.md).
  • Write all sensor readings into a struct and push it to the sensor queue for the nav task
Approach
  • Test each sensor component individually with simple Arduino sketches before integrating into the FreeRTOS task
  • The Adafruit PN532 library (already in platformio.ini) provides examples for reading tag UIDs — start there
  • For the ADC: the ESP32's ADC range and the battery's voltage range may not match — research voltage dividers for your specific battery

Depends on: queue struct definitions from FreeRTOS skeleton, PN532 module, battery, obstacle sensor

ESP32 motor control task

One of the four FreeRTOS tasks. Drives the motor based on commands from the navigation task. Runs at the highest priority — motor timing must not be delayed by anything else. The robot has a single drive motor and no encoder: it never turns, and drives backward to go the other way. The placeholder in tasks/motor_task.cpp only logs commands.

Requirements
  • Read DriveCommands from the drive mailbox (types.h): Stop, or Drive with a signed speed (−255..255; left_speed and right_speed are always equal). The newest command replaces the last. Nav never sends Turn (turns are a placeholder).
  • A Drive with duration_ms stops by itself when the time runs out (a jog pulse), then sets g_drive_done_seq to its seq; duration_ms 0 drives until replaced
  • Changing direction: a Drive the opposite way to the motor's current direction (e.g. a backward jog straight after a forward one) first slows to 0 over REVERSE_RAMP_MS (config.h), then drives the new way. A timed Drive's duration_ms still counts from receipt, ramp included. Never ramp a kill or obstacle stop: those stop at once.
  • Before every cycle: stop the motor while g_motor_kill_flag is set (the battery cutoff), or while the obstacle flag for the side it's driving toward is set (front for a positive speed, rear for a negative one). It must still be able to back away from an obstacle in front.
  • Control the motor driver, an Adafruit DRV8871 (docs/wiring/robot.md): PIN_MOTOR_IN1 / PIN_MOTOR_IN2 in config.h. One input held low while the other is PWMed sets direction and speed; both low lets the motor coast
Approach
  • Test with a standalone sketch: drive forward, stop, reverse. Get the basic motor control working before integrating with FreeRTOS.
  • Then check each flag on the bench: the kill flag stops it in both directions; an obstacle in front stops forward driving but not reversing
  • Check the reversal ramp on the bench: forward, then backward straight away, slows down before reversing; an obstacle during the ramp still stops it at once

Depends on: queue struct definitions from FreeRTOS skeleton, motor driver wired to ESP32, motor type confirmed by ME team

Dashboard API

A REST server on the Pi that serves stored telemetry, alert and command data to the web dashboard. It serves data only: the dashboard itself keeps its own service (farm-dashboard, Next.js on port 3000, docs/PI-SERVICES.md), and the browser calls this API at its own address. This is a Node.js/TypeScript service — review the shared package for the data types the API will serve.

Requirements
  • New service in farm-controller/dashboard-api
  • Serve REST endpoints for: latest robot state, telemetry history over a time range, recent alerts (with optional filtering), and the command history
  • Alerts: the ingester saves every farm/alerts message in the alerts table (the FarmAlert fields plus received_at). Serve it as GET /alerts, returning { "alerts": [...] } of FarmAlerts, newest received_at first (timestamp is the sender's clock), with a limit and optional filters such as severity and source. The dashboard's local source merges them behind the alerts it hears live.
  • Read data from the SQLite database that the ingester populates. Open it in read-only mode so the API and ingester don't conflict.
  • Command history: the ingester saves every operator command in the commands table. Serve it as GET /commands?robot_id= (the filter optional), returning { "commands": [...] }, newest received_at first, at most 10, each { id, robot_id, command, issued_by, issued_at, status: "sent" } with command parsed from JSON — the same shape as the dashboard's own /api/commands (see farm-controller/README.md). The dashboard reads it from NEXT_PUBLIC_DASHBOARD_API_URL. No command endpoint is needed: on FarmNet the dashboard sends commands straight over MQTT.
  • Run as its own systemd unit, farm-dashboard-api, with its port and the database path in /etc/verdant/dashboard-api.env (see "Adding a service" in docs/PI-SERVICES.md). Then set NEXT_PUBLIC_DASHBOARD_API_URL in the dashboard's env file to its address on FarmNet (http://192.168.4.1:<port>) and redeploy.
  • Enable CORS for the dashboard's origins, listed in its env file (http://farmnet.local:3000 and http://192.168.4.1:3000 on the Pi, http://localhost:3000 in development). The dashboard and the API are on different ports, so the browser treats them as different origins on the Pi too.
Approach
  • Use Fastify or Express. Research the framework's patterns for route handlers and CORS.
  • Start with one endpoint (e.g. latest robot state), verify it returns JSON, then add the rest
  • Each endpoint is a SQL query in a route handler — research SQLite query patterns for time-series data

Depends on: ingester running and populating the SQLite database, shared package

Battery monitoring + dock sequence + survival overrides

Final firmware integration: accurate battery measurement, automated docking and charging, and the safety override layer. The survival overrides (nav/survival) and backing onto the dock (Motion::start_docking) are already written; what's left is the battery calibration, the charge contact and testing on hardware with Caleb.

Requirements
  • Battery: Calibrate the ADC-to-percentage conversion against the actual battery's discharge behavior. The percentage in published telemetry should reflect reality.
  • Dock: the robot already backs onto the dock on the rear ToF sensor until DOCK_STOP_CM. Detect the charging contact through a voltage change on PIN_CHARGE_SENSE (GPIO 1: about 2.3 V docked, 0 V off the dock, through a divider; docs/wiring/robot.md) and call NavCore::on_charge_contact(), which stops the motor and publishes dock_connected. Charge complete is published by nav at CHARGE_COMPLETE_PCT.
  • Overrides: already in nav/survival, at the top of the nav loop: battery_low at 20%, a forced return at 15% that a stop still beats, the motor cutoff at 5% (g_motor_kill_flag), and the obstacle events. Verify them on hardware together, with the real battery readings.

Depends on: RFID navigation working, dock hardware from ME team
